# 库存 CSV 导入模式选择

## Goal

让用户在导入库存 CSV 时自行选择“新增”或“覆盖”，既支持日常补货累加，也保留用电子表格
校准绝对库存的能力，避免固定覆盖语义造成误操作。

## Background / Confirmed Facts

- 当前 CSV 采用“系列 × 数字后缀”矩阵，在浏览器本地解析，只把 `{ code, quantity }[]`
  发送到 Worker。
- 当前 `PUT /api/inventory/import` 固定使用覆盖语义；空白不提交，`0` 清零，变更流水记为
  `adjust`。
- 现有普通“批量录入”采用累加语义，流水记为 `entry`。
- 导入 API 必须继续使用当前 Session 的用户 ID，并在同一 D1 batch 中写库存和流水。
- 用户已决定保留两种行为，并在导入时交给用户选择。

## Requirements

- R1. CSV 解析成功后、提交前，用户必须能明确选择“新增”或“覆盖”模式。
- R1a. 每次进入导入流程时默认选择“新增”，因为这是日常补货的主要场景。
- R1b. 每次重新选择 CSV 文件或切换账号时都重置为“新增”；“覆盖”必须针对当前文件主动选择。
- R1c. 预览区使用“新增 / 覆盖”分段按钮；覆盖模式使用警示色和明确说明，但不增加二次弹窗。
- R2. 新增模式把每个非空数量加到现有库存；覆盖模式把每个非空数量设为绝对库存。
- R3. 空白单元格在两种模式下都不修改库存。
- R4. 覆盖模式下 `0` 清零；新增模式下 `0` 不改变库存，也不生成零差值流水。
- R5. 确认按钮与提示必须显示当前模式，降低选错模式的风险。
- R6. 模式随派生后的 items 一起提交；不得接收客户端用户 ID、CSV 原文或文件名。
- R7. Worker 必须严格验证模式和条目；新增与覆盖都只写当前 Session 用户。
- R8. 同批库存更新和流水必须原子提交；新增记 `entry`，覆盖记 `adjust`。
- R9. 保留现有 CSV 格式、大小/数量限制、MARD 色号校验和导入后快照/流水刷新。

## Acceptance Criteria

- [x] AC1. 合法 CSV 预览中可选择新增或覆盖，且提交前能看清当前模式及其语义。
- [x] AC2. 当前库存 80、CSV 数量 100 时，新增结果为 180，覆盖结果为 100。
- [x] AC3. 新增模式的正数流水为 `entry` 且 delta 等于 CSV 数量；`0` 不改变库存或写流水。
- [x] AC4. 覆盖模式继续支持 `0` 清零，并以 `adjust` 记录实际差值。
- [x] AC5. 空白单元格、非法 CSV、未知模式或非法 payload 不产生任何写入。
- [x] AC6. 所有写入只作用于当前 Session 用户，并在一个 D1 batch 内完成库存与流水。
- [x] AC7. 原文件仍只在浏览器解析，既有 CSV 格式和限制保持兼容。
- [x] AC8. `npm run build`、`npm run lint`、模式/API/D1 回归测试通过。

## Out of Scope

- 改变普通“批量录入”功能的累加语义。
- 修改 CSV 矩阵格式、增加 Excel `.xlsx` 支持或上传原文件。
- 修改库存用户隔离、MARD 色卡或数据库表结构。
